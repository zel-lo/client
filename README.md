# zello Client

zello는 회의에서 정한 작업, 담당자, PR과 변경 소식을 여러 GitHub 저장소에 걸쳐 연결하는 팀 협업툴입니다. 이 저장소는 zello의 React 클라이언트입니다.
로그인·저장소 연결·팀 작업·내가 맡은 작업·PR·주간 전체 현황·패치노트·알림·개발 기록·검색·동기화·빌드와 배포 조회는 서버 API를 사용합니다. 비로그인 워크스페이스에서만 샘플 데이터를 사용하며, 세션 확인 중이거나 세션 조회에 실패한 경우에는 샘플 화면으로 대체하지 않습니다. zello는 협업툴의 서비스명이며, 도구 안에서 관리하는 개별 프로젝트와 구분합니다.

## 실행

```sh
npm ci
npm run dev
```

기본 개발 주소: http://127.0.0.1:5173
화면 이동에는 해시 라우팅을 사용합니다. 예: `http://127.0.0.1:5173/#/inbox`.

## 검증 및 빌드

```sh
npm test
npm run build
npm run preview
```

정적 빌드 결과는 `dist/`에 생성됩니다.

## CI와 컨테이너 이미지 배포

`main` 대상 PR과 `main` push에서 GitHub Actions가 테스트·빌드와 Docker 검증을 실행합니다. `main`에서는 검증을 통과한 이미지를 GHCR에 업로드합니다. 실행 방법과 운영 배포 범위는 [CI_CD.md](CI_CD.md)를 참고하세요.

## 주요 화면

- 메인 소개: `/#/`, GitHub 시작하기(로그인·가입 통합): `/#/login` (`/#/signup`은 같은 화면으로 이동)
- 주간 전체 현황: `/#/overview` (로그인 시 실제 프로젝트, 비로그인 시 샘플 미리보기)
- 개인: 알림함, 내 작업(담당 이슈·검토 요청·내 PR)
- 팀: 전체 현황, 팀 작업, 코드 검토, 변경 소식(팀 업데이트·개발 기록)
- 관리: 빌드와 배포, 프로젝트 설정(일반·멤버·저장소 연결·동기화)

이슈·PR 작성 및 연결, 회의 정보, 알림 읽음 상태, 저장소 추가, 패치노트 편집과 설정은 브라우저의 localStorage에 저장됩니다.
GitHub OAuth는 Spring 서버 세션과 연결되어 있습니다. 이슈는 서버에 먼저 저장한 뒤 GitHub에 별도로 발행하며 PR 작성도 실제 GitHub에 반영합니다. 알림은 서버에 저장된 개인 알림을 사용합니다. 자동 웹훅 동기화와 실제 배포 실행은 후속 범위입니다.
로그인·회원가입 버튼은 서버 설정을 확인한 뒤 `/oauth2/authorization/github`로 이동합니다. 개발 시 Vite가 `/api`, `/oauth2`, `/login/oauth2`를 `http://127.0.0.1:8080`으로 프록시합니다. 기본 주소를 쓸 때 `VITE_GITHUB_AUTH_URL`은 비워도 됩니다. 백엔드의 `AUTHENTICATION.md`에 따라 App과 `.env`를 설정하고, `npm run dev -- --port 5173 --strictPort`로 실행해 `http://127.0.0.1:5173/#/login`에서 확인합니다. 성공 callback은 `/auth/callback`이며 `/api/me`로 회원을 확인합니다. 프로필에는 실제 로그인 회원과 로그아웃 버튼을 표시합니다. 로그인한 프로젝트의 팀 작업·PR·주간 전체 현황·패치노트는 서버 데이터를 사용합니다. 토큰은 프론트에 저장하지 않습니다.
샘플 주간 현황의 활동 기준일은 2026년 10월 30일이며 샘플 잔디는 별도 생성한 시각화 데이터입니다. 로그인 프로젝트의 잔디는 summary API의 실제 프로젝트 활동을 사용하며 GitHub 커밋 잔디와 구분해 표시합니다.

## 기술 구성

브랜드 색상은 라이트 `#2F5BFF` / `#E8472B` / `#12151F` / `#F2F4F7`, 다크 `#7C9BFF` / `#FF8F78` / `#FFFFFF` / `#12151F`를 사용합니다. 공통 색상 역할은 `src/styles.css`에 정의하고, 헤더·사이드바·파비콘에 사용하는 원본 Z 로고는 `public/brand/`에 보관합니다. 테마를 바꾸면 로고와 브라우저 테마 색상도 함께 전환됩니다.

React 19, TypeScript, Vite, Tailwind CSS 4, shadcn/ui, React Router, Vitest 및 React Testing Library를 사용합니다.
가져온 shadcn/ui 컴포넌트의 MIT 라이선스는 [SHADCN-LICENSE.md](SHADCN-LICENSE.md)에 보존했습니다.

`docs/`는 로컬 기획 자료로 사용하며 Git 추적 대상에서 제외합니다.

## 실제 저장소 연결과 로그인 상태

GitHub OAuth 로그인 후 **프로젝트 설정 → 저장소 연결**에서 개인·Organization 저장소를 검색·선택·연결합니다. GitHub App 설치 화면으로 이동하거나 PAT를 입력하지 않습니다. 서버에 별도 OAuth App Client ID·Secret과 GITHUB_APP_TYPE=OAUTH 설정이 필요합니다. 로그인 때 read:user·repo·read:org 권한을 승인받으며 repo에는 읽기와 쓰기가 함께 포함됩니다. Organization 정책에 따라 관리자 승인이나 SSO가 필요할 수 있습니다.

홈과 사이드바에는 실제 사용자와 로그인 상태를 표시합니다. HttpOnly 쿠키와 서버의 MySQL 암호화 세션을 사용하며 GitHub 토큰은 localStorage에 넣지 않습니다. 팀 작업과 내가 맡은 작업은 실제 이슈 API를 사용합니다. 기존 대시보드와 검토 요청·알림 등 후속 화면에는 샘플 데이터가 남아 있습니다. 설정과 API는 서버의 AUTHENTICATION.md, REPOSITORY_CONNECTION.md를 참고하세요.

## 가입 안내와 실제 이슈

로그인 성공 후 연결된 저장소가 없으면 `/#/onboarding`으로 이동합니다. GitHub의 조직 접근 승인 페이지를 바로 열 수 있고 돌아오면 목록을 다시 확인합니다. 새 공간은 이름·시작일·종료일 입력, 저장소 보유 여부 선택, 저장소 연결, 팀원 초대 순서로 준비합니다. 저장소가 없으면 GitHub 생성 화면을 안내하고 돌아와 목록에서 연결합니다. 기존 프로젝트가 있으면 현재 프로젝트의 저장소 설정으로 안내합니다. 새 프로젝트는 사이드바 메뉴에서 별도로 시작합니다.

팀 작업 `/#/issues`는 서버의 목록·검색·상태·내 작업 필터·페이지 탐색을 사용합니다. 새 작업은 담당자 없는 할 일로 저장합니다. 진행 중으로 옮기거나 담당자를 선택하면 배정 확인 창이 열리고, 이슈 생성이 성공한 뒤 진행 중으로 옮깁니다. 기존 GitHub 이슈는 담당자만 갱신하며 중복 생성하지 않습니다. 실패한 작업은 할 일에 남아 같은 작업 ID로 재시도합니다. 새로고침·재로그인 후에도 저장한 작업이 유지되며, 보관한 작업은 복원할 수 있습니다. 회의 맥락은 서비스에만 보관하고 설명·완료 조건·담당자·우선순위 라벨을 GitHub에 발행합니다. 조회 전용 멤버의 변경은 서버와 화면 모두 차단합니다.

이슈 상세는 저장 버튼으로 한 번에 반영합니다. 수정 내용이 남아 있으면 먼저 저장해야 발행할 수 있습니다. 충돌 시 입력을 유지하고 최신 내용을 다시 확인할 수 있습니다. GitHub 발행 응답이 유실되면 상태를 다시 읽어 같은 작업의 발행 결과만 확인하며 새 이슈를 자동으로 재생성하지 않습니다.

API와 미구현 범위는 서버의 `ISSUES.md`를 참고하세요.


## 초대와 멤버 관리

프로젝트 설정 → 멤버에서 실제 멤버를 검색하고 초대 링크를 만들 수 있습니다. 권한(멤버/조회자, 소유자는 관리자 포함), 1시간~7일 유효 기간, 선택적인 GitHub 계정을 지정합니다. 원문 링크는 생성 직후 화면에서만 확인할 수 있습니다.

초대 링크는 로그인 후 원래 초대로 돌아오며, 참여 버튼을 눌러야 멤버가 됩니다. 관리자는 멤버를 내보내거나 권한을 변경할 수 있고, 소유자는 다른 활성 멤버에게 소유권을 이전할 수 있습니다. 기존 소유자는 관리자로 남습니다. 프로젝트 나가기는 과거 작업을 보존하며, 재참여에는 새 초대가 필요합니다. 일반 탭의 이름·설명도 서버에 저장됩니다.

권한별 액션, 확인 창, 버전 충돌 안내, 초대 만료/취소/계정 불일치 화면과 OAuth 복귀 경로 검증을 테스트합니다. 서버 정책/API/마이그레이션과 실환경 검증 범위는 `server/zello/COLLABORATION.md`를 참고하세요. GitHub 저장소 접근 권한은 zello 프로젝트 참여와 별도로 검증합니다. 이메일/DM 자동 발송 없이 링크를 복사해 공유합니다.


## 여러 저장소 연결과 화면 갱신

한 프로젝트에 여러 저장소를 연결할 수 있습니다. 연결 화면의 체크박스로 계정/페이지를 오가며 최대 50개를 선택하고 한 번에 연결합니다. 성공한 연결은 유지하며 실패한 저장소만 선택 상태로 남겨 재시도할 수 있습니다. 연결/접근 확인은 기존 개별 API로 수행하고, 전체 선택 처리 후 이슈/PR 수집을 프로젝트별 한 번씩 시작합니다. 이미 연결됐거나 보관된 저장소는 선택할 수 없습니다.

선택창의 일반 focus 이벤트는 저장소·프로젝트 목록을 재조회하지 않습니다. 조직 승인 후 돌아왔을 때와 사용자의 명시적 새로고침으로 갱신하며 선택은 유지합니다. 세션은 화면을 비우지 않고 30초 간격으로 중복 검사를 제한합니다. PR/이슈/멤버 목록도 갱신 시작만으로 기존 화면을 비우지 않습니다.

## 현재 프로젝트의 범위

프로젝트 전환은 사이드바 상단의 프로젝트 메뉴 한 곳에서만 합니다. 내부 이슈·PR·멤버·일반 설정·저장소 탭은 같은 현재 프로젝트를 사용하며 화면마다 다시 선택하지 않습니다. 저장소 연결 컴포넌트는 부모가 전달한 프로젝트만 관리하고 별도 프로젝트 목록·선택 상태를 갖지 않습니다. GitHub 계정/Organization 선택은 이 프로젝트에 연결할 원본 저장소를 찾는 필터입니다.

현재 프로젝트는 사용자별 탭 세션에 기억합니다. 전환 시 이전 프로젝트의 상세·작성창·선택을 정리하고 응답이 늦게 도착한 조회는 취소합니다. 접근이 사라진 경우 다른 프로젝트로 자동 이동하지 않고 사이드바 선택을 안내합니다. 새 프로젝트는 사이드바 → 새 프로젝트 만들기에서 명시적으로 시작합니다.


### 주간 팀 작업 보드

`/issues`는 보드를 기본으로 제공하며 목록으로 전환할 수 있습니다. 기간이 있는 프로젝트는 시작일부터 7일씩 1주차~마지막 주차를 자동으로 선택하며, 기간이 없는 기존 프로젝트는 월~일 주차를 사용합니다. 이전 주의 미완료 작업은 원래 계획일과 같은 ID를 유지한 채 이월 표시로 이어집니다. 할 일은 주차 공통이며, 완료 작업은 완료 주에 표시합니다. 이전 주 화면은 현재 미완료와 그 주의 완료 기록을 조회하며 과거 시점의 상태 스냅샷은 아닙니다.

드래그 또는 작업 메뉴로 순서/단계를 바꾸며 로그인한 사용자의 변경은 version·CSRF와 함께 서버에 저장합니다. 실패 시 표시를 복구하고 재조회할 수 있습니다. 담당자는 팀원 선택으로 지정합니다. 실제 GitHub 이슈를 완료하거나 다시 여는 동작은 확인 창을 거칩니다. 로컬 샘플은 브라우저 저장소를 사용합니다.

단계 이동은 GitHub 작업과 이어집니다. 카드를 끄는 동안 각 열에 놓으면 일어날 일을 표시합니다.

- **할 일 → 진행 중**: 담당자·저장소·계획 주차를 확인한 뒤 **배정하고 이슈 만들기**로 GitHub 이슈를 준비합니다. 이어서 **브랜치 만들기 / 지금은 건너뛰기**를 선택합니다. 기존 할 일(TODO)은 진행 중 열·필터·진행률에 합쳐 표시합니다.
- **→ 검토 중**: 같은 저장소의 열린 PR을 고르는 창을 띄우고 작업 브랜치에서 올린 PR을 맨 앞에 추천합니다. 연결하면 서버가 PR 상태로 단계를 정하며, 초안·수정 요청 PR은 진행 중에 남습니다. 새 PR 작성과 GitHub PR 다시 가져오기도 같은 창에서 할 수 있습니다.
- **열린 PR이 연결된 작업**: 진행 중·검토 중 사이는 PR 상태를 따르므로 손으로 옮기지 않고 이유와 PR 링크를 안내합니다. 할 일과 완료로는 옮길 수 있습니다.

작업 메뉴의 단계 옮기기도 같은 확인 창을 거칩니다. 웹훅에 의한 자동 단계 전환과 초안 PR의 검토 요청 전환은 아직 포함하지 않습니다.

보드는 한 번에 100개를 불러오며 전체/표시 개수와 더 불러오기를 제공합니다. 열의 숫자와 회의 모드 요약은 불러온 작업에 대한 값입니다. 담당자/저장소/상태/주차/검색 필터는 서버의 전체 작업 범위에 적용됩니다. 최초 로딩은 스켈레톤, 갱신은 기존 콘텐츠 유지 방식입니다.


### 프로젝트 시작과 자동 주차

시작일·종료일은 함께 지정하며 최대 10년까지 지원합니다. 종료일을 포함해 주차를 계산하고 마지막 주의 표시 범위는 종료일까지입니다. 시작 전에는 1주차, 종료 후에는 마지막 주차에서 남은 일을 마무리할 수 있습니다. 열린 보드는 날짜가 바뀌면 현재 주차를 갱신하며 직접 고른 과거 주차는 유지합니다.

생성 요청에는 재시도 키를 넣어 응답을 잃어도 중복 공간을 만들지 않습니다. 생성 초안과 키는 사용자별 sessionStorage에 보관하고, 프로젝트 생성 이후에는 URL의 project ID로 이어서 준비합니다. 저장소 연결 실패는 같은 프로젝트에서 다시 시도합니다. 연결이 완료되면 기본 멤버 권한의 72시간 단일 사용 초대 링크를 발급하고, 다른 팀원에게는 새 링크를 만들 수 있습니다. 링크 토큰은 브라우저 저장소에 보관하지 않습니다. 발급 실패 시 프로젝트를 유지하고 초대만 다시 요청합니다.

초대받은 사람은 기존 GitHub 가입·로그인 흐름에서 초대 경로를 유지하고, 내용을 확인한 뒤 참여합니다. zello 참여와 GitHub 저장소 접근 권한은 별도입니다.

## 이슈와 PR 연결

실제 PR 작성에서 같은 저장소의 이슈를 선택한다. 팀 작업의 **PR 작성**으로 시작하면 저장소·제목·이슈가 채워진다. 기존 PR과의 연결·해제는 이슈 상세와 PR 상세 모두에서 서버에 저장하며 보드와 목록에도 표시한다. 초안·수정 요청은 진행 중, 일반 열린 PR은 검토 중, 열린 PR 없이 병합된 PR이 있으면 완료로 반영한다. GitHub 이슈 닫힘과 명시적 완료를 우선하며 유효한 연결이 없어지면 이전 계획 상태로 돌아간다.

새 PR 본문에는 발행된 이슈의 Closes 참조를 추가한다. 기존 PR의 수동 연결·해제는 zello 관계만 변경하므로 GitHub 본문은 GitHub에서 편집한다. GitHub 원본의 Development 연결 자동 수집은 후속 범위다.

## 작업 시작과 Git 명령어

로그인한 팀 작업·내 작업의 작업 상세에서 **브랜치 만들기**를 누르면 GitHub 이슈 번호로 `feat/{번호}` 브랜치를 준비한다. GitHub 발행을 마친 작업에서 사용할 수 있고, 현재 기본 브랜치를 기준으로 생성하며 기존 브랜치는 재사용한다. 이후 **Git 명령어 복사**로 로컬 작업을 시작하고 **이 작업으로 검토 요청 만들기**으로 해당 브랜치와 이슈를 미리 선택한다. 할 일에서 이슈를 만든 직후 같은 브랜치를 선택해서 준비할 수 있다. 상세 조회나 확인 없는 이동만으로는 생성하지 않는다.


## 패치노트 반영 제목

로그인한 프로젝트의 변경 소식은 서버 패치노트 API를 사용합니다. 보드에서 작업을 완료로 옮기면 패치노트 제목을 작성하며, 작업 상세에서 완료할 때도 같은 제목을 입력합니다. 이슈의 원래 제목과 패치노트에 소개할 제목은 별도로 보관합니다.

GitHub에서 닫힌 이슈나 병합된 PR은 가져오기 이후 패치노트 초안에 모이고, 제목을 작성하기 전에는 **반영 사항 작성 필요**로 표시됩니다. 변경 소식에서 반영 제목을 작성·수정할 수 있으며, 미작성 항목이 있으면 초안 저장은 가능하지만 공개는 할 수 없습니다. 재수집은 사람이 작성한 제목을 덮어쓰지 않습니다. 서버 DB에는 Flyway V12와 V13 적용이 필요합니다.


## PM용 주간 전체 현황

전체 현황은 이번 주 진행률, 먼저 확인할 작업, 사람별 담당 현황, 최근 완료한 작업으로 구성합니다. 로그인한 프로젝트는 `GET /api/projects/{projectId}/dashboard`를 사용합니다.

진행률은 이번 주 계획과 이전 주에서 이어온 미완료 작업을 기준으로 계산하며 할 일·다음 주 작업·이전 주 완료 기록은 제외합니다. 이번 주 완료 수에는 연결된 이슈가 없는 병합 PR도 포함하므로 계획 작업 완료 수와 다를 수 있습니다. 담당자 없는 작업, 3일 이상 지난 검토 요청 또는 열린 PR, 수정 요청 PR은 확인 목록에서 바로 상세를 열 수 있습니다. 업무 담당에는 이름과 맡은 일만 표시하고, 항목을 누르면 오른쪽 패널에서 담당 업무를 확인하며, 최근 완료 목록에는 패치노트 반영 제목을 우선 표시합니다. GitHub 변경은 기존 가져오기 기능으로 수집한 기록 기준입니다.


## 로그인·가입 통합

메인에서 시작하기를 누르면 하나의 GitHub 시작 화면으로 이동합니다. **GitHub로 계속하기**로 처음 방문한 사용자는 가입하고 기존 회원은 로그인합니다. 기존 `/signup` 주소는 `/login`으로 연결하며 초대 복귀 경로, OAuth 오류와 재연결 조건을 유지합니다. 로컬 로그인에는 프런트 외에 8080 포트의 Spring 서버도 실행되어 있어야 합니다.


전체 현황 상단에서 주차를 선택하거나 이전·다음 주로 이동할 수 있습니다. 프로젝트 기간이 있으면 해당 기간의 1주차부터 마지막 주차까지 선택하고, 이번 주 버튼으로 현재 주차에 돌아옵니다. 선택한 주는 URL의 `week`에 남아 새로고침해도 유지됩니다. 완료 수는 해당 주의 완료일 기준이며 진행·검토 항목은 현재 상태이므로 과거 시점의 상태를 재현한 수치로 표시하지 않습니다. 업무 담당 항목을 누르면 오른쪽 패널이 열립니다.

변경 소식 첫 화면은 패치노트 안의 반영 사항을 하나씩 펼쳐 새 기능·개선 사항·오류 수정 섹션으로 나눕니다. 각 항목에 변경 발생일을 11월 8일 형태로 반복 표시하고, 반영 제목·관련 작업/PR·제목 편집을 바로 확인합니다. 별도 반영 항목 없이 직접 작성한 글은 팀 소식 섹션에 표시합니다. 패치노트 보기에서 전체 본문과 공개 기능을 사용합니다. 할 일 생성 개수 제한은 없으며 보드는 100개씩 더 불러오기, 목록은 30개씩 페이지 탐색을 사용합니다.


## 출시 전 사용자 경험 정리

전체 현황은 이번 주의 수정 요청 → 오래 기다린 검토 → 담당자 없는 작업 순으로 다음 확인 항목 하나를 안내하고 실제 작업/PR 상세로 연결합니다. 과거 주차에는 현재의 다음 행동 안내를 섞지 않습니다. 빈 프로젝트에는 첫 작업 등록을 안내하며 정상 진행 중이라는 표현을 사용하지 않습니다.

하단의 활동 잔디는 `GET /api/projects/{projectId}/summary`의 `contributions`를 사용합니다. 최근 1년을 표시하고, 평면/3D 전환·키보드 탐색·라이트/다크 테마를 유지합니다. 서버의 UTC 일별 집계이며 커밋 수가 아님을 밝힙니다. 오류·조회 중·활동 없음은 구분하고, 실제 프로젝트에서 임의의 샘플 활동을 만들지 않습니다.

알림 읽음 처리·전체 읽음은 서버 저장 성공 후 반영합니다. 개발 기록은 activities API로 조회하며 관리 이벤트의 내부 식별자 문자열은 본문에 노출하지 않습니다. 검색은 현재 프로젝트의 실제 작업을 검색합니다. 동기화에서는 기존 이슈/PR 수집 API를 순서대로 호출하고, 일부 실패·접근 불가 저장소·남은 수집 범위를 안내합니다. 화면 새로고침과 GitHub 수집은 구분합니다.

## 처음 사용하는 팀을 위한 안내

작업 등록과 코드 검토 요청의 입력 항목은 접지 않고 모두 표시합니다. 필수·선택 항목, 구체적인 예시, zello 저장과 GitHub 반영 여부를 안내합니다. 작업 흐름·PR·브랜치 설명은 별도 도움말로 제공합니다. 프로젝트 준비를 마치면 첫 작업 등록 화면으로 이동합니다.
